# Design: Learner readings behind a judge port, eval-first and audit-first (RFC-0007 revision)

Generated by /office-hours on 2026-10-02
Branch: main
Repo: shettydev/mukti
Status: APPROVED
Mode: Builder

## Problem Statement

Mukti reads each learner message with regex and substring lists, and the verdicts are
wrong in both directions. RFC-0007's own measurements (commit `ed0651d`): "The $40 is
sunk. It shouldn't factor in." scores 0.02 and is marked not-understood; "Thanks, but I
still don't get why..." sets `conclusionReady = true`.

Those verdicts are durable. They move `consecutiveSuccesses` / `consecutiveFailures`,
change the scaffold level, and are written to `KnowledgeState`.

Two things this session added to the RFC's diagnosis, both checked against the code:

1. **One verdict is written to every concept the session carries.** Three processors
   do this: `dialogue-queue.service.ts:437-451`,
   `conversations/services/queue.service.ts:644-659`, and
   `thought-map/services/thought-map-dialogue-queue.service.ts:495-511`. Each writes a
   single `demonstratedUnderstanding` boolean to every ID in
   `gapResult.detectedConcepts` plus `rootGap`.
   `knowledge-gap-detector.service.ts:500-507` re-adds all context concepts each turn
   and `:582-609` substring-matches every active concept.
2. **Bad reading creates a quiet path to answer-giving.** A terse, correct learner
   fails the evaluator twice, `FAILURES_TO_ESCALATE` is 2
   (`scaffold-fade.service.ts:15`), and the stored level climbs toward 4
   (`DIRECT_INSTRUCTION`), where direct answers are allowed. Nothing measures this.

## What Makes This Cool

Mukti's promise is "more questions than answers", and nothing in the codebase checks
whether a reply hands over the answer. This design turns that into a measured number:
the answer-giving rate per scaffold level, split by how the reply came to be generated
at that level.

The second part: the judge is a plug-in slot. A hosted vendor has to beat a plain
model call on your own labelled turns before it earns a place in the request path.

## Constraints

- Solo maintainer. Each adapter is something to keep working.
- Local mode (`muktiai` CLI on the user's own `claude` or `agy`) is a first-class
  surface. Those users did not agree to send text to another hosted service. Local
  mode has no queue; jobs run inline in the API process (`common/queue/inline-runner.ts`).
- No reference answers exist. Sessions are about the learner's own open-ended problem.
- The pre-evaluation at `dialogue-queue.service.ts:325` feeds quality directives before
  generation, so it needs a verdict inside the turn.
- Fade and BKT writes run after generation but before the reply is emitted (emit at
  `dialogue-queue.service.ts:479`, `conversations/services/queue.service.ts:703`).
- A local CLI run takes about 40 s with `agy`
  (`knowledge-gap-detector.service.ts:516-518`). `LocalCliClientFactory` spawns one
  child per call and has no abort path.
- TypeSafe / Jev: latency and domain accuracy are unpublished, per the RFC. Nobody in
  this session could vouch for it independently. `@typesafe-ai/sdk` is not installed.

## Premises

1. The damage is durable, and it has two causes: the turn is misread, and the verdict
   is attached to every stored concept. The fan-out is stopped by ending the writes
   (P1). The misread is fixed for fading by M5, or by the stated fallback if M5 misses
   its bar.
2. Without a reference answer, no judge here can say whether the learner is right.
   What a judge can read from text is **engagement**: did the learner answer what was
   asked and give a reason that bears on it. That is enough to decide whether to keep
   asking questions or add support. It is not evidence of mastery, so it never writes
   to `KnowledgeState`. `grasp` gets zero weight.
3. The reply audit is the first model-backed feature. It changes no behaviour. It is
   validated against hand labels before its number is published.
4. The labelled probe set is the asset; the judge vendor is replaceable. Per-turn
   snapshots start now, in every mode, because stored messages carry no per-turn level,
   concepts, or verdict.
5. Local mode is first-class. A model reading can serve it because the fade decision
   for a turn is not needed until the learner's next message arrives.

## Cross-Model Perspective

Codex was unavailable (its native binary is missing: `spawn ... codex ENOENT`), so the
cold read came from a fresh Claude subagent. Same harness as the primary session, so
its agreement counts for less than a different model's would.

- **Coolest version:** an open, contestable learner model. Mukti shows its reading
  ("I read that as: you've settled the sunk-cost question. Right / Not yet") and the
  learner can overrule it. Each overrule is a label.
- **What excites the author most:** "Mukti's core promise is never checked."
- **Existing tools:** promptfoo as the eval runner; MRBench (BEA 2025 shared task) for
  human "revealing of the answer" labels. Both recalled from memory by the reviewer;
  licence, ownership, and dataset size are unverified.
- **Weekend build:** gate heuristic BKT writes, build the port with heuristic and
  local-CLI adapters, score them on a probe file, and snapshot every turn.
- **Premises challenged:** 1, 4, and 5. All three were revised.
- **Also noted:** RFC Alternative B (ask a generation model for JSON) is already in
  production in `misconception-detector.service.ts`, on the platform key.

## Approaches Considered

- **A. Stop the bleeding.** Heuristic fixes and snapshots, no judge. Not chosen alone:
  fading stays phrase-counted and answer-giving stays unmeasured. It became M1 and M2.
- **B. Judge port, eval-first, audit-first (chosen).** Below.
- **C. Open learner model.** The learner confirms or corrects Mukti's reading. Not
  chosen now: it adds a step to every turn and self-report inflates mastery. Kept as a
  later label source for B's port.

## Recommended Approach

Six milestones. M1 to M4 each stand alone. M5 and M6 are conditional on a bar. All
three processors (node dialogue, conversation, thought map) are covered by every
milestone.

### The port

One combined call per turn, made after the reply is emitted. All adapters return the
same decision-level result, so they are compared on the same thing.

```text
TurnReading
  engaged      yes | no | unclear     (unclear = abstain)
  givesAnswer  boolean | null         (null when the adapter cannot judge replies)
  raw?         adapter-specific
```

**`engaged` rubric, used for labelling and for every adapter's prompt.** Judged from
the transcript text alone. `yes`: the reply answers the question that was asked and
gives at least one reason that bears on that question. `no`: it does not answer, or it
answers with no reason, or the "reason" is connective filler with no content. Whether
the answer is correct is not judged. `unclear` / "can't tell": the text does not show
it either way.

Consequences of that rubric for the RFC's probes:

- "The $40 is sunk. It shouldn't factor in." is `yes`.
- The connective-stuffed reply ("because since the ticket was already paid, therefore
  I should go...") is also `yes`: it answers and gives a reason, and the reason is the
  fallacy. Its expected label changes from the RFC's `false`. A learner reasoning from
  a wrong belief needs a counter-question, not more scaffolding, so `yes` is the right
  input to fading. Catching the false belief is the misconception detector's job
  (Open Question 3).
- A new negative probe replaces it: connective filler with no reason, such as
  "Because of the reasons, since it is what it is, therefore I would say so." Expected
  `no`.

The judge does not receive the scaffold level. RFC-0002's stricter thresholds at lower
levels apply only to the heuristic; a model reading is level-independent. That is a
change to RFC-0002 semantics and is recorded in the RFC revision.

| Adapter               | Transport                                                                       | Who pays                       | Where text goes                                     |
| --------------------- | ------------------------------------------------------------------------------- | ------------------------------ | --------------------------------------------------- |
| `HeuristicJudge`      | In-process; `engaged` = today's `demonstratesUnderstanding`; `givesAnswer` null | Nobody                         | Nowhere                                             |
| `ModelJudge` (hosted) | One JSON-prompted call via OpenRouter, model pinned by `LEARNER_READING_MODEL`  | Platform key                   | OpenRouter, as generation does today                |
| `ModelJudge` (local)  | One run through `LocalCliClientFactory`                                         | The learner's CLI subscription | The provider the learner already chose              |
| `TypeSafeJudge`       | RFC-0007's System One request                                                   | Platform key                   | TypeSafe (new data processor; privacy policy first) |

Every bar below is measured per (transport, model) pair. `readingVersion` includes the
prompt version and the model id. A local provider that has not cleared the bar gets
`shadow` at most. The first hosted candidate is the model the misconception detector
already uses; it is a candidate, not a choice.

`ModelJudge` reverses the RFC's rejection of Alternative B. The objections were
uncalibrated numbers under thresholds, generation latency on the reply path, and
billing BYOK keys. Categorical decisions remove the thresholds, the call runs after the
reply, and hosted mode uses the platform key.

### M1. Stop the bad writes (human: ~1 day / CC: ~45 min)

- Fix `countConceptMentions` (`response-evaluator.service.ts:326`) to match concept
  names and space-separated IDs.
- Add contrast guards to the three patterns in `conclusion-detector.service.ts:30-37`:
  "but" / "still" after a closure word, a trailing question, and "I'll be honest".
- Apply P1 and P2 in all three processors.
- No write-scope rule is built, because nothing writes. Whoever re-enables writes
  inherits the requirement: a verdict may reach only the concepts the turn is about.

### M2. Per-turn snapshots (human: ~2 days / CC: ~1 hour)

New collection `turn_snapshots`, written in every mode by all three processors. One
record per `(sourceType, sourceId, nodeId, turnIndex)`. No message text. Index on
`(userId, createdAt)` for account deletion. No TTL.

```text
userId, mode (hosted | local)
evaluationLevel    stored level, used to judge the learner's message
generationLevel    max(gap level, stored level), used for the reply
gapLift            generationLevel - evaluationLevel for this reply (0 if none)
fadeTransition     { from, to, cause: failure | success | none }   stored-level change
storedLevelOrigin  fade | gap_first_exchange   (a conversation's first exchange can set it)
conceptsInPlay[]
preReading         { source, engaged }             in-turn; heuristic until M6
postReading        { source, engaged, status }     what the judge observed (M5)
applied            { source, engaged, at }         what actually drove fade (M5)
audit              { givesAnswer, source, status } (M4)
readingVersion, createdAt
```

Snapshot writes, and the later `postReading`, `applied`, and `audit` updates, are
best-effort: logged on failure, never thrown, never a cause for a retry of the turn.
The RFC's `learner_turn_judgments` collection and its TTL stay as written, for raw
TypeSafe answers in M6 only.

### M3. Port, probes, and `ModelJudge` (human: ~1.5 weeks / CC: ~1 day)

- The port, `HeuristicJudge`, and `ModelJudge` with both transports.
- **Synthetic probes** in the repo (`probes.jsonl`): the RFC's probes relabelled under
  the rubric, plus more written by hand. CI runs `HeuristicJudge` on these and prints
  a confusion table. Model adapters never run in CI.
- **Private probes** in `.mukti/probes/` (gitignored): hand-labelled real turns,
  scored locally with `bun run eval:readings`; results are pasted into the RFC.
- Labels: `engaged` per learner turn, `givesAnswer` per assistant reply.
- Probes taken from turns recorded after M2 carry their level and concepts. Older
  turns do not, so `HeuristicJudge` is scored on them at all five levels and its best
  level is reported. That favours the baseline, on purpose.
- **Sizing.** The target is set by the rarest label that gates a bar: at least 40
  `givesAnswer` positives and 40 `engaged: no` turns in total, found by targeted
  sampling, not by reading sessions in order. Expect 200 or more labelled turns.
- **Scoring rules, fixed before measuring.**
  - Half the private probes are for tuning prompts. The other half is held out.
  - A further slice of 30 real turns is reserved, unseen, for each ship decision (M4,
    M5, M6). The held-out half is scored at most once per `readingVersion`.
  - Metric: macro-F1 on yes/no. "Can't tell" turns are excluded and counted. An
    adapter answer of `unclear` on a labelled turn counts as a miss.
  - Every bar needs at least 20 positives and 20 negatives in the data it is scored
    on. Fewer means the bar is not met.
  - Model adapters run 3 times. The worst run must clear the bar, and the margin must
    exceed the 90% bootstrap interval of the difference.

### M4. Reply audit (human: ~3 days / CC: ~2 hours)

- The combined call runs after the reply is emitted and writes only to the snapshot,
  so ordering does not matter. Hosted: platform key. Local: opted-in learners only.
- **Bar before any rate is published:** precision at least 0.80 and recall at least
  0.70 for `givesAnswer`, with real and synthetic positives reported separately.
- **Noise floor:** the false-positive rate on real held-out negatives. A cell whose
  rate does not exceed it is marked as within noise.
- **What is reported**, per `generationLevel`:
  - the raw answer-giving rate;
  - at levels 0 to 3 that rate is the violation rate (RFC-0002 forbids direct answers
    below level 4);
  - at level 4 it is not a violation. It is split per reply: **fade-reached** when
    `evaluationLevel` is 4 and `storedLevelOrigin` is `fade`; **gap-lifted** when
    `evaluationLevel` is below 4 or the origin is `gap_first_exchange`. Fade-reached
    answers are the misread-driven number from Problem Statement point 2;
  - any cell with fewer than 30 replies is reported as insufficient data.
- **If the bar is missed:** no model-derived rate is published. The hand-labelled
  probes give a hand count, published as exactly that.
- **Hosted cost:** unknown until measured. Token counts are recorded in `shadow`.
  `LEARNER_READING_SAMPLE_RATE` and a daily call cap are set from those numbers before
  the judge runs on anyone's traffic but the maintainer's.

### M5. Model reading drives fade (human: ~1 week / CC: ~half a day)

**Ship bar:** per (transport, model), `ModelJudge` beats `HeuristicJudge` on `engaged`
by at least 0.10 macro-F1 under the M3 rules, and every synthetic probe maps to its
expected label.

**Sequencing: settle the previous turn when the next one arrives.** The fade decision
for turn N only matters when turn N+1 starts.

- Concept and gap-detection persistence stay inline, as today. Only the stored level,
  the counters, and the transition history move.
- After reply N is emitted, the combined call runs and writes `postReading` and
  `audit` to snapshot N. It never touches dialogue state.
- When turn N+1's processor starts, before it loads state, it **settles** turn N:
  - Hosted waits up to 3 s for a pending reading. Local does not wait.
  - If `postReading` is `ok` with `yes` or `no`, fade is applied from it.
  - If it is `unclear`, no transition (the "no prior assistant message" behaviour).
  - If it is missing, late, or failed, the heuristic `ResponseQuality` is recomputed
    from the stored message, `evaluationLevel`, and `conceptsInPlay`, and fade is
    applied from that.
  - `applied` records which source was used. A reading that arrives after settlement
    is stored in `postReading` and changes nothing.
- One actor (the next turn's processor), one order (turn order), no new field on
  existing schemas. A process exit in local mode loses the pending reading and the
  turn settles on the heuristic.
- Local runs are not cancelled. The judge runs alongside the next reply's generation.
- A session's last turn is never settled. Nothing reads its level until a next turn.

**Modes.** `off`: today's inline writes. `shadow`: today's inline writes, plus the
call, plus a dry run of the settle step that logs what it would have applied. `apply`:
settle step live.

**Before `apply`:** a Jest concurrency suite (two messages in quick succession, late
reading, failed reading, process restart) passes; two weeks of `shadow` show no turn
settled twice or out of order in the dry-run log; and for local, at least 60% of turns
would have settled on a model reading. Below 60%, local stays `shadow` or off, since
the learner would pay for readings that rarely count.

**If M5 misses its bar:** P3's fallback, `FADE_ESCALATION=gap_only`.

### M6. `TypeSafeJudge`, only if it wins

- Scope: the in-turn pre-evaluation (`engaged`) and wrap-up detection. Nothing else.
- Bars: beats hosted `ModelJudge` on `engaged` by at least 0.05 macro-F1; beats the
  fixed heuristic on `wantsWrapUp` by at least 0.10 (this label is collected only when
  M6 is attempted); p95 latency at or under 800 ms.
- After M6: the pre-evaluation uses TypeSafe when it answers in time, else the
  heuristic. The settle step reuses the turn's TypeSafe reading when one exists, so no
  second paid call is made for that turn; otherwise `ModelJudge`.
- Mapping changes from RFC §5.4: `grasp` weight 0.
  `u = 0.50 * answer_fit/3 + 0.25 * P(transfer) + 0.25 * P(probing_question)` as a
  start. Under the rubric the terse correct answer and the fallacy answer both score
  about 0.50 and both expect `yes`, so one threshold can pass both; thresholds are
  re-tuned on the tuning half so every synthetic probe maps to its label.
  `rawScores.depth = answer_fit/3`. `signals.mentionsConcept` comes from the fixed
  keyword match. Abstention reads `confidence(answer_fit)` only.

### What changes in RFC-0007

- **Title and abstract:** the mechanism is a judge port; TypeSafe is one conditional
  adapter.
- **§3 Goals:** Goal 2 (downstream contracts unchanged) and Goal 3 (one shared request
  per turn) are dropped; Goal 7 narrows to `givesAnswer`. Non-goal "no local judging"
  becomes opt-in.
- **§5.4:** formula, thresholds, `signals`, and abstention as in M6; no BKT mapping.
- **§5.5:** the turn is read in-turn by the heuristic and after the reply by a model.
- **§5.6:** per-level report as in M4; two audit signals deferred.
- **§6:** the port is `TurnReading`; `LearnerTurnJudgment` becomes TypeSafe's `raw`.
- **§7:** still no existing schema changes; adds `turn_snapshots`.
- **§8:** Alternative B is `ModelJudge`, no longer rejected.
- **§9:** learner text also goes to a JSON-prompted model on the platform key and, with
  opt-in, to the learner's own CLI provider.
- **§11, §12:** flags are the ones in the decisions table; phases become M1 to M6;
  rollback steps follow the flags. Phase 1's 150 production turns become the private
  probe set.
- **§13:** OQ-5 (local opt-in) and OQ-8 (`grasp`) are decided here.
- **§14 decision log, reversed:** "Judgments feed existing contracts; no downstream
  changes" and "One fan-out request per learner turn". Kept: shadow before live,
  heuristics as fallback, audit is measurement-only, policy stays in code.
- **RFC-0001 and RFC-0002:** note that knowledge writes are frozen (P1, P2) and that
  model readings are level-independent.

## Open Questions

1. **What would count as mastery evidence?** P1 freezes knowledge tracing. Unfreezing
   it needs a signal this design does not have. The open learner model (Approach C)
   and the Assignment's "from memory" column are the two leads.
2. **Prerequisite checker on frozen values.** It can still name a `rootGap` from stale
   mastery numbers. Leave it, neutralise it, or decay old values?
3. **Wrong but well-reasoned answers** read as `engaged: yes`. The misconception
   detector is the guard for false beliefs, but it fails open at 500 ms and is skipped
   under a local CLI. Whether that is enough is untested.
4. **One labeller.** A second person labelling a 30-turn subset, with agreement
   reported, would show how far the bars can be trusted.
5. **TypeSafe evidence.** No independent latency or accuracy numbers exist.
6. **Carried from the RFC:** OQ-4 (regenerate on a high `gives_answer`) and OQ-6 (the
   three-of-four `signals` fallback in `ScaffoldFadeService.isSuccessfulResponse`).
7. **External labels.** Does MRBench's "revealing of the answer" wording transfer to
   open-ended sessions? Check size and licence first.
8. **Should `gap_only` be the default now**, not only the fallback? It closes the
   answer-giving path in M1 at the cost of changing fade behaviour before any evidence.

## Success Criteria

- M1: the RFC evidence-table rows for closure pass as tests; a multi-word concept test
  passes; tests in all three processors prove no `KnowledgeState` write happens with
  `KNOWLEDGE_WRITES=off` and that the knowledge term is 0.5.
- M2: a snapshot is written in `off`, local, and hosted modes by all three processors,
  and a forced write failure does not fail the turn.
- M3: the label targets are met; the synthetic-probe table runs in CI.
- M4: the audit meets its bar and the per-level table is in the RFC with noise-floor
  and insufficient-data cells marked, or the hand count is published instead.
- M5: the ship bar and the before-`apply` conditions are met, or `gap_only` is set.
- M6: the bars are met, or it does not ship.

## The Assignment

Before writing any adapter: open your own `.mukti/local-db` (9.5 MB of real sessions)
and pull 30 learner turns with the assistant reply that followed each. Label three
columns, and note how long it takes.

1. **`engaged`** (yes / no / can't tell), from the text alone, using the rubric above.
2. **Did I actually understand at that point?** (yes / no / can't tell), from memory.
   Only you can fill this column.
3. **Did Mukti give away the answer?** (yes / no).

What the counts decide:

- If more than 40% of column 1 is "can't tell" across everything labelled, engagement
  is not readable from text either, and the model reading stays `shadow`-only. If it
  is 20% or less, proceed. In between, label 30 more once; a result still in between
  counts as usable, with the share reported next to every bar.
- How often columns 1 and 2 disagree is the size of the gap between engagement and
  understanding in your own sessions. That number is the starting evidence for Open
  Question 1.
